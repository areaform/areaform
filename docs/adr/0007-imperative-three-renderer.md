# render-3d uses imperative Three.js, with one merged mesh per Level

The 3D preview lives in its own package, `render-3d`, and drives Three.js imperatively, as `render-2d` drives PixiJS ([ADR-0004](0004-imperative-pixi-renderer.md)): `createRenderer3D` returns a framework-free renderer (`update(doc)`, `setLevel`, `setView`, `getCamera` / `setCamera`), and `editor` wraps it in a thin React component. Camera control is Three.js's own `OrbitControls` (damping, zoom to the pointer, never below the floor).

We considered react-three-fiber, Babylon.js and the polygon extrusion of map libraries (deck.gl, MapLibre). react-three-fiber would make the renderer React-only and reconcile thousands of Zones through React, which ADR-0004 rejected for the same reasons. Babylon.js is a game engine, heavier than a preview needs, and would be a second rendering ecosystem next to Pixi. Map libraries can extrude a footprint but cannot cut door gaps in Walls.

What to draw is decided in a pure layer (`buildLevelMeshes`: Level → vertex arrays, tested without WebGL). It writes every Level into one opaque mesh (plus one for see-through Zones), with flat normals and colour per vertex, so orbiting costs a draw call or two however large the plan is. That meets ADR-0004's target of 5,000 Zones and 10,000 Walls at 60 fps. The Level is rebuilt only when its object, or the Connections list, changes ([ADR-0005](0005-snapshot-history-and-reference-diffing.md)). On the stress Space a rebuild takes about 40 ms, about 12 ms of it in `wallOutlines`. That is over the 16 ms edit budget, but the 3D view never edits: rebuilds come from undo, redo or the host. If that changes, cache each Element's triangles by object identity.

Wall joins come from `core`'s `wallOutlines`, the same mitred footprints the 2D renderer draws, so the two views always agree. Colours come from render-2d's `Theme`, so a host's category colours apply in both views. What only 3D needs (background, Wall faces, Stop heights) is a separate `Theme3D`. Door height is a renderer option (`doorHeight`, 2.1 m), not a model field: the schema stays unchanged until someone needs doors of different heights.

**Consequences:** `three` is a peer dependency of `render-3d`, loaded through a dynamic `import()` on the first `createRenderer3D` call, so pages that only show 2D never download it. The 3D view needs WebGL 2 (Three.js has dropped WebGL 1), and `isWebGLAvailable()` lets a UI grey out its 3D switch.
